## Черга UX-покращень (за відгуком користувача 2026-07-14)

### U40 (P1): Версія додатку = номер останнього PR

**Запит.** «Хочу, щоб остання цифра версії була така, як номер PR — тоді
видно, який останній PR у бранчі».

**Аналіз.** Версія зараз — `v0.1.0` з `frontend/package.json` через
vite define (`__APP_VERSION__` + sha + дата збірки в hover). Номер останнього
змерженого PR надійно витягується з історії:
`git log --grep="Merge pull request #" -1` → «Merge pull request #42 …»
(репозиторій мержить через merge-коміти, тож патерн стабільний).

**Фікс.**
1. `frontend/vite.config.ts`: обчислити `__APP_PR__` (номер останнього
   merge-PR у поточній гілці; `0`, якщо не знайдено — напр. shallow clone).
2. `frontend/src/version.ts`: `versionLabel = v{major}.{minor}.{PR}`
   (патч із package.json замінюється номером PR); `fullVersion` лишає sha+дату.
3. Повернути `VersionBadge` поруч із брендом у desktop-хедері редактора
   (після редизайну він лишився тільки у футері «?»-діалогу та «⋯»-шторки —
   залишок задачі B1 зі старого баг-плану).
4. У футері «?»-діалогу показувати повний рядок (`v… · sha · дата`) видимим
   текстом, не тільки в hover.

**Перевірка.** `npm run dev` → бейдж показує v0.2.«актуальний PR»; після
мержу нового PR і перезапуску — цифра зросла. Vitest: юніт на парсер номера.

### U41 (P1): Чіп вибраного файлу на стартовому екрані

**Запит.** «Обрав m4a — на UI не видно, що саме обрано; нема поля зі шляхом».

**Аналіз.** Після вибору файлу з'являється лише кнопка «Транскрибувати» —
сам файл ніде не показано. «Loaded-file chip» був у макетах редизайну
(SPEC.md §5, upload-phone.html), але в кроці 7/8 його не реалізували.
Ім'я файлу ніде не зберігається: `useAudioUpload.handleFile(file)` знає
`file.name`, але передає далі тільки `AudioInfo` з бекенда (file_id/duration).
Шлях до файлу браузер не віддає принципово (безпека) — показуємо ім'я.

**Фікс.**
1. `projectStore`: додати `audioFileName: string | null` (поруч з
   `audioBlob`/`audioFileId`); `useAudioUpload.handleFile` зберігає
   `file.name`; запис із мікрофона → «Запис із мікрофона».
2. `App.tsx`: коли `audioFileId` є — чіп над кнопкою «Транскрибувати»:
   `🎵 {ім'я} · {тривалість}` + кнопка ✕ (скинути файл і обрати інший).
   Всі три тіри (на телефоні — над sticky-кнопкою).
3. Тривалість: бекенд `/api/upload` зараз повертає `duration_sec: 0.0`
   (заглушка) — прочитати реальну тривалість через pydub при завантаженні
   (він уже підключений після B2a).

**Перевірка.** Обрати m4a → видно чіп з ім'ям і тривалістю; ✕ повертає
дропзону; запис з мікрофона теж дає чіп. Vitest на стор; ручна перевірка
3 тірів.

### U42 (P1): Помітна «Нова транскрипція» після завершення

**Запит.** «Коли пройшла транскрипція — не видно, як почати нову пісню».

**Аналіз.** Дія існує, але захована: desktop/tablet — рядок «✨ Нова» всередині
меню «Файл ▾»; телефон — «←» у хедері (з confirm) та рядок у «⋯»-шторці.
Користувач на ноутбуці її не знайшов — отже, меню недостатньо. Плюс
виявлена розбіжність: телефонна «←» питає підтвердження, а «Нова» з меню
Файл — ні (ризик втратити незбережену роботу одним кліком).

**Фікс.**
1. Desktop/tablet-хедер: видима ghost-кнопка «✚ Нова» поруч зі «Зберегти»
   (лейбл + іконка, не icon-only). Рядок у меню «Файл ▾» лишається.
2. Уніфікувати підтвердження: будь-який шлях до нової транскрипції питає
   «Відхилити поточну транскрипцію…?», якщо є незбережені зміни
   (використати спільний handler з confirm — зараз він є лише в phone-back).
3. (Дрібне) Після успішного експорту PDF/MusicXML — toast «Збережено. Почати
   нову?» з кнопкою — природний момент для наступної пісні.

**Перевірка.** На 1280px кнопку видно одразу; confirm спрацьовує на всіх
шляхах; після скидання — стартовий екран.

### U43 (P2): Іконки інструментів у селекторі

**Запит.** «Замість тексту — може, іконки інструментів?»

**Аналіз.** `InstrumentSelector` — сегментований контрол з текстом
(Скрипка/Фортепіано/Гітара). Іконка без підпису погіршить доступність і
зрозумілість; іконка + підпис — найкраще з обох.

**Фікс.**
1. Емодзі-іконки в сегментах: 🎻 Скрипка · 🎹 Фортепіано · 🎸 Гітара
   (іконка перед лейблом; на вузьких екранах іконка зверху, підпис дрібним
   знизу — сегменти стають квадратніші, tap-зона ≥44px лишається).
2. `aria-label` повний (з назвою), емодзі з `aria-hidden`.

**Перевірка.** Візуально на 3 тірах; радіогрупа читається скрінрідером.

## Живі баги (перенесено з 07-BUGFIX-PLAN)

### B3 (P1): Всі ноти показує шістнадцятими (реально — восьма з крапкою)

Статус: **чекає на діагностику** — потрібен проблемний запис користувача,
прогнаний через бекенд з увімкненими логами (B2, PR #40): дивимось
`Detected tempo`, `Meter: … level=…` і `Duration distribution`.

Гіпотеза: детектований BPM занижений у ~3 рази (восьма з крапкою 0.75 долі →
0.25 = шістнадцята). Якщо підтвердиться — самодіагностика рівня темпу в
`SegmentationService` (аналог tie-flood retry з U34): якщо >60% нот після
квантизації — шістнадцяті і темп авто-детектований → повторити квантизацію
з BPM×2/×3, обрати варіант із меншою часткою 1/16 та меншим залишком
квантизації. Тест: синтетичний кейс + регресія que_lindo (66 BPM).

### B4 (P2): Тональність — сусіди по квінтовому колу (D major замість G)

Статус: **передумова підтверджена** логами B2 на реальному записі:
G major=0.783 vs D major=0.767 — розрив 0.016, межовий випадок.

Фікс: розширити tiebreak у `key_detector.py` — якщо топ-1 і топ-2 ближче
порога І вони сусіди по квінтовому колу, вирішує (а) тонічність фінальної
ноти, (б) розрізняльний ступінь у мелодії (для G vs D: чи звучав C-натуральний
— тоді C# із D major неможливий → G). Тест: юніт-кейс G-major мелодії з
C-натуральним + регресія наявних кейсів key_detector і real_recordings.
